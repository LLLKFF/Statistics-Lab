# Statistics Lab｜参考架构与开发路线

> **状态**：规划基准  
> **适用版本**：Statistics Lab v1.2 及后续版本  
> **更新日期**：2026-09-10  
> **用途**：沉淀外部项目对标结论，指导 Statistics Lab v1.3–v1.6 的产品、统计、数据与工程建设。  
> **上位规范**：[DESIGN.md](../DESIGN.md)。如本文与品牌操作手册冲突，以 `DESIGN.md` 为准。

---

## 1. 核心结论

Statistics Lab 的后续建设采用以下组合思路：

1. **借第一个项目的产品壳与工程组织**；
2. **借第二个项目的指标目录、计算覆盖和数据呈现方式**；
3. **借第三个项目的市场连接器抽象与加密资产覆盖思路**；
4. **统计推断、证据标准、研究状态和结论表达由 Statistics Lab 自主建立**。

一句话概括：

> **第一个负责体验，第二个负责内容密度，第三个负责币圈接入模型，Statistics Lab 自己负责证据标准。**

“参考”不等于整体复制。产品结构、接口思想和视觉交互可以研究；代码复用必须逐项核对许可证、依赖、技术栈和可验证性。

## 3. 对标一：daily_stock_analysis

### 3.1 值得借鉴

该项目适合作为 Statistics Lab 的“壳子”与工程参考，重点包括：

- React、Vite 与 FastAPI 的前后端分离；
- Web、API、桌面端和自动化任务的多入口组织；
- 数据源基类、字段标准化、优先级与失败回退机制；
- 研究任务进度、历史报告、配置管理和状态反馈；
- 移动端适配、明暗主题、通用卡片与页面组件；
- Docker、GitHub Actions、测试和发布流程；
- API Schema、服务层、Repository 层与前端组件的分层思路。

建议重点参考的不是某一张页面，而是以下完整闭环：

`数据源 → 标准化 → 计算任务 → 结构化结果 → 报告历史 → Web 展示`

### 3.2 不应照搬

Statistics Lab 不应继承其核心产品叙事中的以下部分：

- LLM 买卖建议、持仓建议或具体点位判断；
- 将“决策仪表盘”包装为操作依据；
- 自动交易或以成交为目标的功能；
- 依赖模型生成但无法追溯计算过程的结论；
- 在研究结果之前优先建设大量通知渠道和配置项；
- 用综合分数掩盖样本、估计量、区间与稳健性细节。

其数据源管理思路值得借鉴，但部分核心文件体量较大。Statistics Lab 应保留接口思想，并按资产、能力和数据类型拆分实现，避免形成新的单体文件。

### 3.3 在 Statistics Lab 中的对应落点

- `apps/web`：研究网站与移动端界面；
- `api`：只读研究 API、任务 API 和结果 API；
- `src/data/providers`：数据源适配与标准化；
- `src/jobs`：可复现研究任务与状态管理；
- `reports`：人可读研究报告；
- `src/repositories`：研究结果、元数据和版本索引。

## 4. 对标二：myhhub/stock

### 4.1 值得借鉴

该项目在“数据呈现与计算覆盖”方面更有参考价值，主要包括：

- 基本面、技术面、资金、行情和人气等多类别字段；
- 基于 Pandas 与 TA-Lib 的指标批量计算；
- K 线、成交量、指标副图和形态标记的组合呈现；
- 筹码分布及成本区间的可视化；
- 日期枚举、历史区间和批量任务；
- 数据库存储、历史结果保留和面向筛选的字段设计；
- Bokeh 图表中的缩放、悬停、联动和指标选择；
- 指标、形态、策略和回测模块相对清晰的业务分类。

Statistics Lab 可将这些内容转化为“研究变量目录”和“图表组件库”，尤其适合：

- 技术指标的描述统计；
- 筹码分布及其稳健性研究；
- K 线形态的事件研究；
- 横截面分组与条件筛选；
- 不同日期、市场和参数下的批量复算。

### 4.2 必须区分：指标计算不等于统计推断

该项目的优势主要是指标丰富、计算覆盖广和页面信息密度高。Statistics Lab 不能把这些特征直接等同于证据强度。

任何指标或策略进入正式研究，至少还要补充：

- 明确、可证伪的原假设与备择假设；
- 效应量，而不只报告方向或胜率；
- 标准误和置信区间；
- 原始 p 值与多重检验调整结果；
- 时间序列依赖和横截面相关修正；
- Newey-West、区块 Bootstrap 或其他合适方法；
- 样本内、验证集和最终样本外的严格分离；
- 交易成本、滑点和换手敏感性；
- 参数扰动、子样本和安慰剂检验；
- 数据窥探、幸存者偏差和前视偏差检查；
- 统计显著性与经济意义的分别说明。

因此，第二个项目适合作为**变量、指标和呈现素材库**，而不是 Statistics Lab 结论口径的来源。

### 4.3 不应照搬

- Bootstrap 3、jQuery 和服务端模板的旧式前端结构；
- 将大量字段、数据表和业务配置集中在单个超大文件；
- 只用上涨概率、命中率或简单区间收益评价策略；
- 把技术指标的计算一致性直接解释为研究结论正确；
- 将选股、自动交易和 Statistics Lab 的证据研究混在一起。

## 5. 对标三：StockSharp

### 5.1 值得借鉴

StockSharp 对加密资产方向最有价值的部分，是成熟的交易基础设施抽象，而不是直接提供 Statistics Lab 的统计结论。

可重点研究：

- Connector 与消息适配器的分层；
- 证券、交易所、市场板块和合约标识的标准化；
- 行情订阅、取消订阅、断线与重连语义；
- Level 1、逐笔成交、盘口、K 线等不同数据类型；
- 历史行情、实时行情、存储和仿真的分离；
- 现货、期货、期权、外汇和加密资产的统一建模思路；
- CEX、DEX、链上数据和第三方数据商的能力分类；
- 手续费、滑点、订单与持仓等模块的边界设计；
- 指标、策略、统计、回测和报告的模块化组织。

### 5.2 许可证与技术栈边界

StockSharp 当前仓库的 [LICENSE](https://github.com/StockSharp/StockSharp/blob/c049b1f9ee1653b158a9303115779a1f48e5534e/LICENSE) 明确采用自定义许可，不属于通用开源许可证；仓库材料的使用受其 EULA 和官网条款约束。部分连接器示例还要求通过其私有 NuGet 源获取组件。

因此：

1. **不得默认复制、移植或重新分发 StockSharp 代码**；
2. 可以研究公开呈现的架构概念，但具体实现应采用 clean-room 方式；
3. 如未来确需直接集成，必须先确认当时有效的 EULA、费用和分发范围；
4. StockSharp 为 C#/.NET 主栈，Statistics Lab 为 Python 主栈，不应为了连接器覆盖而整体迁移技术栈；
5. 若采用 StockSharp，可考虑独立 sidecar/service，而不是侵入统计核心；
6. 在许可未确认前，不得把其连接器能力写成 Statistics Lab 已经拥有的功能。

### 5.3 加密市场的初始范围

Statistics Lab 的加密市场模块应先聚焦**只读研究数据**，不接交易权限。首批统一数据类型建议为：

- 现货与永续合约 OHLCV；
- 逐笔成交；
- Level 1 与有限档位订单簿；
- 资金费率与下一次结算时间；
- 标记价格、指数价格和基差；
- 持仓量；
- 清算数据；
- 合约规格、最小变动单位与乘数；
- 交易所状态、数据缺口与异常记录。

初期可优先覆盖 Binance、Bybit、OKX 等具有代表性的中心化交易所，但每个接入都应使用官方公开 API 或许可清晰的数据源。

## 6. 许可证治理

### 6.1 当前判断

| 项目 | 当前许可证判断 | 对 Statistics Lab 的含义 |
|---|---|---|
| daily_stock_analysis | MIT | 可在满足许可证和版权声明要求后复用代码；仍需逐文件检查第三方内容 |
| myhhub/stock | Apache-2.0 | 可在遵守 Apache 2.0、NOTICE 与修改声明要求后复用代码 |
| StockSharp | 自定义许可 / EULA | 不按普通开源项目处理；默认只做架构研究，不复制代码 |

### 6.2 Statistics Lab 的处理原则

Statistics Lab 当前尚未在仓库根目录声明自身 `LICENSE`。在许可证确定之前：

- 仅吸收思想、信息架构、接口需求和公开事实；
- 不批量复制外部源码、静态资源、图标或文档；
- 如需移植 MIT 或 Apache-2.0 代码，必须单独登记来源、提交 SHA、原许可证与修改内容；
- 新增 `THIRD_PARTY_NOTICES.md` 前，不将第三方代码并入主分支；
- 对许可不清晰的实现使用 clean-room 重新实现；
- 每个 Pull Request 增加“第三方来源与许可证”检查项；
- 许可证检查通过不代表统计正确，统计验证仍需独立进行。

建议在 v1.3 中完成 Statistics Lab 自身许可证选择和第三方依赖登记规范。

## 7. 目标架构

### 7.1 分层结构

`
数据源与原始快照
        ↓
Provider 适配与标准化
        ↓
研究数据集与版本清单
        ↓
Evidence Engine 统计推断
        ↓
结构化 Research Result
        ↓
报告、图表、API 与网站
`

建议的逻辑目录如下：

~~~text
statistics-lab/
├── apps/
│   └── web/                    # React/Vite 研究网站
├── api/                        # FastAPI，只读查询与任务编排
├── src/
│   ├── data/
│   │   ├── providers/
│   │   │   ├── equity/
│   │   │   └── crypto/
│   │   ├── normalization/
│   │   ├── quality/
│   │   └── lineage/
│   ├── evidence/
│   │   ├── estimators/
│   │   ├── inference/
│   │   ├── robustness/
│   │   └── multiple_testing/
│   ├── studies/                # 可复用研究实现
│   ├── jobs/                   # 研究运行、状态与缓存
│   └── repositories/           # 结果和元数据索引
├── schemas/                    # 数据与研究结果契约
├── reports/                    # 正式报告
├── notebooks/                  # 探索与复现
├── figures/                    # 可追溯图表产物
├── methods/                    # 方法笔记
├── papers/                     # 论文与复现
├── failures/                   # Rejected 与证据不足研究
└── docs/
    └── adr/                    # 架构决策记录
~~~

该目录是目标结构，不要求一次性迁移。v1.3 应先建立最小骨架，并通过一项研究验证其必要性。

### 7.2 前端与 API

前端借鉴 daily_stock_analysis 的现代工作台形式，但页面语义改为证据研究：

1. **Home**：定位、最新研究、方法论边界；
2. **Research Library**：按板块、状态、证据等级、市场和方法筛选；
3. **Study Page**：假设、数据、估计量、图表、稳健性、局限和复现入口；
4. **Methods**：方法说明和代码模板；
5. **Papers**：论文卡、批判性精读、复现与文献图谱；
6. **Failures**：被拒绝、证据不足和样本外失效研究；
7. **About**：品牌原则、作者信息与免责声明。

API 初期保持只读为主：

- `/api/studies`
- `/api/studies/{study_id}`
- `/api/results/{study_id}`
- `/api/figures/{study_id}`
- `/api/methods`
- `/api/papers`
- `/api/failures`
- `/api/jobs/{run_id}`

### 7.3 Evidence Engine

Evidence Engine 是 Statistics Lab 与三个参考项目真正拉开差异的核心。它应统一生成结构化研究结果，而不是让每个 Notebook 自由输出。

建议每项结果至少包含：

- 研究编号与版本；
- 假设、估计对象和识别策略；
- 市场、样本范围与数据截止日期；
- 数据源、数据版本、提取时间和处理哈希；
- 原始样本量与有效样本量；
- 点估计、效应量、标准误与置信区间；
- 原始 p 值及多重检验调整值；
- 依赖结构与修正方法；
- 样本内、验证集和样本外结果；
- 成本与滑点假设；
- 稳健性、安慰剂和参数敏感性；
- 统计意义与经济意义；
- 已知局限和失效条件；
- `Prototype / Validated / Rejected` 状态；
- A–D 证据等级及逐项理由；
- 代码、数据清单、图表和报告链接。

### 7.4 统一图表组件

图表是证据，不是装饰。首批组件建议包括：

- 效应量与置信区间图；
- 事件研究图；
- 滚动估计与结构变化图；
- 样本内与样本外对照；
- 参数敏感性热力图；
- 交易成本敏感性曲线；
- 分组收益与分布图；
- 安慰剂结果分布；
- 稳健性矩阵；
- K 线、指标与筹码分布联动图；
- 数据缺口与质量诊断图。

任何图表必须能够追溯到结构化结果、数据版本和生成代码。

## 8. 数据接口设计

### 8.1 Provider 最小契约

所有股票和加密数据源均应实现统一概念接口：

- `capabilities()`：声明支持的市场、资产和数据类型；
- `fetch_instruments()`：证券与合约元数据；
- `fetch_bars()`：OHLCV；
- `fetch_trades()`：逐笔成交；
- `fetch_order_book()`：盘口快照或增量；
- `fetch_auxiliary()`：资金费率、持仓量等辅助数据；
- `normalize()`：转换到内部 Schema；
- `health_check()`：可用性、延迟和配额；
- `provenance()`：来源、版本、参数和提取时间。

每项能力必须显式声明，不允许通过空值假装支持。

### 8.2 加密资产标准字段

至少统一：

- `venue`；
- `instrument_id`；
- `instrument_type`；
- `base_asset` 与 `quote_asset`；
- `contract_type`、乘数与到期日；
- `event_time` 与 `received_time`；
- `timezone`；
- `source` 与 `source_version`；
- `is_final`；
- `quality_flags`。

原始数据与标准化数据分层保存。研究不得只保留最终 CSV，而丢失来源和转换过程。

### 8.3 加密数据质量风险

所有加密研究必须额外检查：

- 交易所时钟偏差；
- 不同资金费率周期；
- 现货与永续的符号映射；
- 合约换代、下架与幸存者偏差；
- 稳定币计价差异；
- 交易所宕机和数据缺口；
- 盘口快照与增量丢失；
- 异常成交和可疑交易量；
- 跨交易所价格不同步；
- 数据商对清算、持仓量等字段的不同定义；
- 研究截止时间后的数据回填造成的前视偏差。

## 10. 方法论红线

本文涉及产品、指标和加密数据扩展，但不得改变 Statistics Lab v1.2 的品牌宪法。

### 10.1 始终坚持

- 把市场说法转化为可证伪假设；
- 同时报告效应、区间、不确定性和局限；
- 严格区分研究状态与证据等级；
- 保留 Rejected、失败和证据不足结果；
- 优先使用样本外与稳健性证据；
- 对数据、代码、参数和版本保持可追溯；
- 明确统计显著性不等于经济意义；
- 允许公开回答“暂时不知道”。

### 10.2 明确禁止

- 具体点位预测、行情喊单或买卖建议；
- 自动交易作为 Statistics Lab 的核心功能；
- 把技术指标或模型输出直接包装成可靠信号；
- 把 Prototype 包装成 Validated；
- 只展示成功回测，隐藏失败研究；
- 先看全样本结果，再伪装成事前假设；
- 用复杂界面、综合评分或漂亮图表掩盖薄弱证据；
- 把样本量大直接等同于高等级证据；
- 用 LLM 生成无法复算、无法追溯的核心统计结论；
- 因参考项目功能丰富而无边界扩张。

## 11. 架构决策原则

后续每一项重大开发应回答：

1. 它解决了哪一类研究问题？
2. 如果不做，会影响哪项正式研究？
3. 输出能否进入统一 Research Result Schema？
4. 是否增强了可复现性、证据质量或读者理解？
5. 是否引入新的数据、许可证或隐私风险？
6. 是否与“不做预测、不做喊单”的边界冲突？
7. 是否有更小的纵向切片可以先验证？
8. 如果结果失败，失败记录将保存在哪里？

原则上，先完成一项真实研究的端到端闭环，再扩展通用平台；先验证数据与统计口径，再追求页面数量和连接器数量。
